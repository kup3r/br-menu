# Telegram-бот продаж и админ-панель BR

Админ-панель находится **в Telegram**, отдельного сайта администратора нет.
Сервис содержит webhook бота и HTTPS API проверки ключей в одном процессе.
Платежи — разовые покупки срока в Telegram Stars; автосписаний нет.
Ни токен бота, ни секреты сервера не нужны покупателям или клиентской dylib.

## Что работает

- Покупатель: условия → тариф → Stars → ключ; «Мои ключи» и продление.
- Счёт фиксирует Telegram ID покупателя, цену и дни. Ключ создаётся только после
  `successful_payment`. Повторы одного платежа не дублируют ключ/продление.
- Ключи на 1–3650 дней, отсчёт с создания или первой активации, 1–5 устройств.
- `/admin`: создание до 100 ключей одним файлом, просмотр всех ключей с пагинацией,
  поиск, продление, блокировка/разблокировка, подтверждаемый сброс устройств.
- Создание тарифов и включение/выключение продаж кнопками.
- Статистика, список последних 20 платежей, возврат Stars с подтверждением.
- `/support`, `/paysupport`, `/terms`, `/cancel`.
- PostgreSQL хранит ключи, заказы, оплаты, сессии, привязки, журнал действий.
  Состояние незаконченной формы бота временное; после рестарта открой /admin снова.
- Ключи хранятся в зашифрованном виде; для поиска используются HMAC. Устройства
  представлены хешем случайного ID установки, без UDID и аппаратного отпечатка.
- Доступ администратора проверяется заново в каждом действии, а не по видимости кнопок.

## Перед первым запуском

Нужны бот, созданный в @BotFather, твой числовой Telegram ID, PostgreSQL (например,
Neon) и HTTPS-хостинг Python. Секреты задаются в окружении хостинга, не в GitHub.

```sh
cd licensing
python -m venv .venv
# Windows: .venv\Scripts\activate
# Linux/macOS: source .venv/bin/activate
pip install -r requirements.txt
python scripts/generate_secrets.py
```

Скопируй `.env.example` в локальную `.env` или заполни те же переменные на хостинге:

| Переменная | Значение |
|---|---|
| `BOT_TOKEN` | Токен из BotFather |
| `ADMIN_IDS` | Твой числовой ID; несколько ID через запятую |
| `DATABASE_URL` | PostgreSQL URL; Neon URL с `sslmode=require` поддерживается |
| `PUBLIC_URL` | HTTPS-адрес сервиса; на Render можно не задавать — используется `RENDER_EXTERNAL_URL` |
| `SUPPORT_URL` | Ссылка на твою поддержку в Telegram |
| `TERMS_TEXT` | Твои реальные условия: продукт, сроки, устройства, возвраты |
| `WEBHOOK_SECRET` | Случайный секрет из генератора |
| `KEY_PEPPER` | Секрет HMAC из генератора |
| `KEY_ENCRYPTION_KEY` | Ключ Fernet из генератора |

Сохрани резервные копии PostgreSQL, KEY_PEPPER и KEY_ENCRYPTION_KEY: смена этих
секретов без миграции сделает прежние ключи/сессии недоступными.

```sh
uvicorn brlicense.app:create_app --factory --host 0.0.0.0 --port 8000 --no-access-log
```

При запуске создаются начальные таблицы и устанавливается webhook с секретным
заголовком. Не запускай polling другого процесса на том же токене. Таблицы
создаются для первой установки; будущие изменения схемы требуют миграций.

Проверка: `GET /health`, затем `/start` и `/admin` в личном чате с ботом. Сначала
создай бесплатный тестовый ключ через админку. Тарифы по умолчанию отсутствуют:
цены и открытие продаж определяешь ты. До реальных продаж проверь оплату через
отдельного бота в Telegram test environment.

### Render

`render.yaml` можно использовать как Blueprint с путём `licensing/render.yaml`.
Либо создай Web Service: Root Directory `licensing`, Build Command
`pip install -r requirements.txt`, Start Command как в render.yaml, Health Check
`/health`. Данные хранятся в PostgreSQL, диск Render не нужен.

Для продаж нужен доступный сервис: Telegram ждёт ответ pre-checkout максимум
10 секунд. Хостинг, который засыпает, может не успеть принять платёж; это не
исправляется хранением ключей в боте. Выбирай постоянную работу процесса.

## Возвраты и восстановление

Возврат предварительно переводит платёж и ключ в `refund_pending`. При таймауте
доступ остаётся приостановленным: система не делает повторную финансовую операцию
вслепую. Подтверждённый возврат записывается также по Telegram `refunded_payment`.
При неоднозначном результате проверь платёж в Telegram перед любыми действиями.
Возврат отключает весь связанный ключ, включая последующие продления. Смешанные
случаи решаются вручную: при необходимости администратор выдаёт новый ключ на
оставшийся оплаченный срок. Не разблокируй платёж, возврат которого подтверждён.

Если выдача оплаченного ключа в чат оборвалась, покупатель нажимает «Мои ключи»:
результат сохранён до отправки сообщения. Пачки розыгрыша доступны в «Все ключи».

## API для приложения

`POST /v1/licenses/activate`:
```json
{"key":"BR-…","device_id":"random-install-uuid"}
```
Ответ: `token`, `expires_at` и `session_expires_at` (Unix seconds).
Активация того же устройства не расходует ещё один слот и заменяет его сессию.

`POST /v1/licenses/check`, заголовок `Authorization: Bearer TOKEN`:
```json
{"device_id":"random-install-uuid"}
```
Ответ: `valid: true`, даты окончания. Сессия скользящая до 1 часа, но не дольше
срока ключа. Доступ закрывается при блокировке, возврате, истечении срока или
сбросе устройства. Проверка устройств/оплат использует блокировки PostgreSQL.
Активации ограничены 10 запросами в минуту с одного адреса; проверки — 600.

Проверка ключа не исполняет код клиента и не изменяет игровые серверы.

## Лицензируемая dylib

`Inject/LicenseGate.swift` подключён к `BRMenuEntry` только при `BRMENU_LICENSED`.
Обычная сборка v18 остаётся прежней. Лицензируемая сборка сначала показывает окно
ввода ключа; только после подтверждения сервером создаёт меню. Ключ и случайный
ID установки сохраняются в iOS Keychain. Проверка повторяется каждые 60 секунд,
а после возврата приложения из фона выполняется новая активация. При отказе или
ошибке связи меню удаляется и игровые переключатели останавливаются. Поэтому
отзыв не мгновенный: активный клиент узнает о нём при следующей проверке.
Старые уже распространённые v18 автоматически платными не становятся.
Модифицируемый нативный клиент нельзя сделать полностью неуязвимым к обходу.

После запуска сервера сборку можно сделать с телефона через GitHub Actions:
после объединения ветки открой workflow **Test Telegram licensing and build licensed client** → Run workflow →
указать HTTPS API URL и `https://t.me/ИМЯ_БОТА`. Артефакт `BRMenu-Licensed` содержит
готовую dylib. Ручной запуск без адресов только проверяет компиляцию и не публикует
клиент с тестовым адресом. Аналогично локально на Mac:

```sh
BRMENU_LICENSED=1 \
BRMENU_LICENSE_API_URL=https://YOUR-SERVICE.example \
BRMENU_LICENSE_BOT_URL=https://t.me/YOUR_BOT \
bash scripts/build_dylib.sh
```

Для новой IPA используй `scripts/prepare_ipa.py` с исходной IPA и этой dylib,
затем переподпиши готовую копию. Все платежи и настройки админки остаются в боте.

## Проверки

```sh
pip install -r requirements-dev.txt
python -m pytest -q
# Реальные блокировки и гонки: отдельная тестовая БД, её таблицы удаляются!
TEST_DATABASE_URL=postgresql+asyncpg://... python -m pytest -q
```

Тесты создают собственные таблицы. Никогда не указывай production БД в
`TEST_DATABASE_URL`. CI проверяет также PostgreSQL 16 и компиляцию клиента SDK.
Никакие реальные Stars во время этих автоматических тестов не списываются.
